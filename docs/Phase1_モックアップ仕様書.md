## 1. 背景・目的

現行の3D見回り画面は、空・地面が単色でランドマークが消火栓1本のみのため、プレイヤーからは「果てしない地平線を歩いているだけ」に見えるという課題が報告された。これに対し、モバイル性能を維持しながら現実世界（平泉町）に寄せた見た目を実現するため、**近景／中景／遠景の3層構造による段階的改善計画**を策定し、そのうち低コスト・即効性のある **Phase 1** を先行してモックアップ化し、動くデモとして検証した。

Phase 1のスコープは次の4点に限定される。

1. 空のグラデーション化＋雲
2. 霧（Fog）による地平線のぼかし
3. 地面テクスチャ（芝生調）の追加
4. 道路帯の追加（さらに実データ反映まで拡張）

## 2. モックアップの範囲・意思決定の経緯

| 論点 | 決定内容 |
|---|---|
| モックアップの範囲 | Phase 1のみ（空グラデーション・霧・地面テクスチャ・道路帯） |
| 生成物の形態 | 静的画像ではなく「動くアプリ画面」（HTML/JS操作可能デモ） |
| 道路の描き方 | 当初は直線の帯を想定 → ユーザー要望により実際のLeaflet道路形状に一致させる方向へ拡張 |
| 道路データ取得手段 | Overpass API系ミラーが軒並みタイムアウト／空応答となったため、**OSRM Routing API**（`router.project-osrm.org`）から実ルートのジオメトリ（座標列）を取得する代替手段を採用 |

## 3. 実施内容の詳細

### 3.1 空（Sky）

- 単色の空（`#B5D0EB`）を、天頂〜地平にかけての **グラデーション球体**に変更。
- 浮遊する雲スプライトを4枚配置し、静的でのっぺりした印象を軽減。

### 3.2 霧（Fog）

- `THREE.Fog`（もしくは`FogExp2`相当）を導入し、**概ね14m〜95m**の範囲でフェードアウトするよう設定。
- 霧の色を空の地平色と一致させることで、地面と空の継ぎ目（地平線）を自然にぼかし、「単調な直線の地平線」という指摘を解消。

### 3.3 地面テクスチャ

- Canvas生成による**芝生調の繰り返しテクスチャ**を地面に貼付。
- プレイヤー移動時にテクスチャが流れることで、速度感・移動している実感（オプティカルフロー）を演出。

### 3.4 道路帯（当初仕様 → 実データ反映へ拡張）

**当初仕様（直線帯）**
- 消火栓脇に、中央線入りアスファルト風テクスチャの帯を配置。
- 等間隔に街灯ポールを配置し、奥行きの目印とする。

**拡張仕様（実道路データ反映）**
ユーザーからの「Leafletの道路に合わせて配置できないか」という要望を受け、以下を実施。

1. **道路データ取得**
   - Overpass API公開ミラー複数（overpass-api.de、kumi、osm.ch、fr、nchc.org.tw、monicz.dev、openstreetmap.ru、osm.jp 等）へ接続を試みたが、タイムアウトまたは空応答（対象範囲内に該当データなし）が続いた。
   - 代替として **OSRM Routing API** を使用し、平泉字志羅山付近の実在ルート（起点 緯度経度 (38.987472, 141.115946) 〜 終点 (38.98195, 141.1119)、県道300号経由）のジオメトリを取得。
   - 取得したルートは約1,254.6mだが、モックアップでは至近区間（約400m、カーブを含む）を抽出して使用。
2. **座標変換**
   - 取得した緯度経度の座標列を、原点（lat 38.9869, lng 141.1170）基準のローカルX/Z平面座標に変換（既存の`latLngToWorldPosition()`と同一の変換方式）。
3. **ミニマップ（Leaflet）反映**
   - SVGパス（`M...L...`）で実道路の折れ線をそのまま描画。
   - 黄色い帯＝道路、破線＝中央線、青い円＝縄張り範囲、青い点＝プレイヤー、赤い点＝消火栓。
   - ジョイスティック操作で青い点（プレイヤー）がリアルタイムに道なりを移動。
4. **3D空間反映**
   - 道路座標の各点で進行方向ベクトルを算出し、90度回転させた法線ベクトルで道幅（5m）分オフセットして左右の頂点列を生成、リボン状メッシュ化。
   - カーブ部分は台形状セグメントが連結され、滑らかに曲がって見える。
   - 中央線・アスファルト質感テクスチャのUV縦方向（V座標）は「区間ごとの累積距離 ÷ 道幅」で計算し、引き伸ばされず自然に流れるよう処理。
   - 道路脇に等間隔のポールを法線方向オフセットで配置し、カーブに沿った奥行きの目印とした。
5. **消火栓の配置調整**
   - 道路から少し脇に離した位置（道沿い60m地点、道路に対し垂直方向へ3.4mオフセット）に再配置し、「道端に立っている」自然な見え方に調整。

### 3.5 既存機能との整合（Phase 1範囲内で維持したもの）

- 点検ボタン（「てんけんする」）は消火栓との距離が一定値（モックアップでは2.4〜2.6m程度）以内で有効化。
- 縄張り境界に到達すると「ここからそとは、ぼくのなわばりじゃない」という趣旨のトースト通知でプッシュバック演出。
- タイマー・点検数・スコア表示、キャンセルボタン等の既存UIは変更なし。

## 5. 技術的な実現手順（実装引き継ぎ用サマリ）

1. Overpassまたは他の経路データソース（本件ではOSRM）から、対象道路の緯度経度ノード列を取得する。
2. 既存の`latLngToWorldPosition()`と同一の変換式で、各ノードをXZローカル座標に変換する。
3. 各点について前後の点から進行方向ベクトルを計算し、これを90度回転させた法線ベクトルを用いて道幅分オフセットした左右の頂点列を生成する。
4. 生成した頂点列からリボン状メッシュ（道路面）を構築する。
5. テクスチャのV座標（縦方向）は「区間ごとの累積距離 ÷ 道幅」で算出し、テクスチャの伸縮を防ぐ。
6. 同じ緯度経度データをLeafletの2Dミニマップ側にもSVGパスとして描画し、3D側と形状を完全一致させる。
7. 消火栓等のランドマークは、道路からのオフセット（道沿い距離＋垂直距離）で位置決めし、道端に自然に配置する。

## 6. 未確定事項・要検討仕様

Phase 1のモックアップ検証を踏まえ、Phase 2以降の本実装に向けて以下が未確定である。

| # | 項目 | 内容・論点 |
|---|---|---|
| 1 | 道路データの正式取得経路 | Overpass公開ミラーが不安定なため、本番運用でのデータ取得元（自前Overpassサーバー、OSRM、国土数値情報、平泉町オープンデータ等）をどれにするか要決定。 |
| 2 | 道路・建物データのパイプライン化 | 取得した道路ジオメトリを`public/data/roads.json`として保存し、ビルド時またはゲーム内で自動読み込みする仕組みが未実装。 |
| 3 | 対象エリアの道路網の範囲 | 猫ごとの縄張り（半径300m程度）に対し、どこまでの道路網（主要道路のみ／生活道路まで含むか）をカバーするか未確定。 |
| 4 | 道幅・ポール間隔等のパラメータ調整 | モックアップでは道幅5m等を仮設定。実際の道路種別（県道・生活道路等）に応じた可変パラメータ化が必要か検討中。 |
| 5 | Phase 2（建物）との統合方法 | 道路メッシュに合わせて建物ブロックをどう配置するか（道路からのオフセット、街区の簡易生成ロジック）が未設計。 |
| 6 | パフォーマンス検証 | 実データ反映後の道路メッシュ・ポール数増加が、低スペック端末で30〜60fpsを維持できるか実機検証が未実施。 |
| 7 | 消火栓のオフセット配置ルールの一般化 | 本モックアップでは1本のみ手動オフセット調整。複数消火栓・全対象エリアに適用する自動配置ロジックが未定義。 |
| 8 | ミニマップと3Dの同期範囲 | 現状は単一ルートのみ対応。交差点・複数道路が交わるケースでのSVG描画・メッシュ生成方法は未検証。 |

## 7. 次のステップ候補

1. **実データパイプライン化**: OSRM/Overpass等から複数道路・交差点データを取得し`public/data/roads.json`化。ゲーム内自動読み込みのビルドスクリプトを作成する。
2. **Phase 2（建物）の追加**: 道路沿いに簡易建物ブロックを配置し、街並みらしさを付与する。
3. **見た目の微調整**: 道幅・ポール間隔・テクスチャ色味等のパラメータチューニング。
